# SystemWorkerを使用した4DでのOpenSSL活用

Al Mahdi Bakkali（4D Inc. テクニカルサポートエンジニア）

テクニカルノート 26-02

## 概要

本書では、4DアプリケーションにOpenSSLを統合し、非同期実行パターンを用いて暗号関連リソースを生成する方法を解説します。本テクニカルノートでは、4D.SystemWorkerクラスを活用してシェルコマンドをブロックせずに実行し、秘密鍵（Private Key）、証明書署名要求（CSR：Certificate Signing Request）、自己署名証明書を生成します。実装例として、安全なデータ交換のための署名付きXMLドキュメントの作成や、生成した証明書を設定した4D Webサーバーの運用など、実践的なユースケースを紹介します。コールバックベースの非同期アーキテクチャを採用することで、計算負荷が高く時間のかかる暗号処理を実行している間も、ユーザーインターフェースの応答性が損なわれたり、ほかのアプリケーションプロセスがブロックされたりすることはありません。

## はじめに

今日のデジタルセキュリティにおいて、秘密鍵、証明書署名要求（CSR）、署名付きの証明書やドキュメントといった暗号関連リソースを生成・管理・活用する能力は、もはやオプションの機能ではありません。コンプライアンス、電子インボイス（e-invoicing）、安全なデータ交換のための基本的な要件です。規制産業の組織には、データセキュリティと本人確認に関する厳格な義務が課されており、堅牢な暗号基盤は事業運営に欠かせないものとなっています。さらに、電子インボイスシステムやサプライチェーン自動化の普及に伴い、送信データの真正性と完全性を検証できる高度なデジタル署名の仕組みを、開発者が実装する必要性が高まっています。

本書は、**4D.SystemWorker**クラスを使用して4D開発環境にOpenSSLを統合するための包括的な技術マニュアルです。アプリケーションのスレッドをブロックしてしまう**LAUNCH EXTERNAL PROCESS**による従来の同期実行パターンから脱却し、System Workerの非同期機能を取り入れることで、オペレーティングシステムのコマンドラインインターフェースと直接やり取りする、応答性の高い高性能なアプリケーションを構築できます。非同期アプローチはアーキテクチャ上の大きな進化であり、暗号処理をバックグラウンドで実行している間も、メインのアプリケーションスレッドはユーザー操作の処理やほかの並行タスクに対応できます。鍵のサイズやシステムリソースによっては数秒から数分かかることもある証明書の生成中に応答性を維持しなければならないアプリケーションにとって、ブロッキング実行からノンブロッキング実行への移行は特に重要です。

本テクニカルノートのデモ用4Dアプリケーションはクロスプラットフォームに対応しており、WindowsとmacOSの両方のオペレーティングシステム向けに開発されています。クロスプラットフォームで動作させるため、OpenSSLのバイナリパスを動的に検出し、各プラットフォームのデフォルトのインストール先から実行ファイルを自動的に見つけ出します。この自動検出により、エンドユーザーの設定の手間が大幅に減る一方で、カスタムインストールにも柔軟に対応できます。OpenSSLが標準以外のフォルダーにある場合は、ユーザーが実行ファイルのパスを手動で指定できます。指定したパスはアプリケーションのセッションに保存され、以降のすべての処理で使用されます。

### OpenSSLのインストール

開発マシンにOpenSSLがまだインストールされていない場合も、サポート対象のどちらのプラットフォームでも簡単にインストールできます。

### Windowsへのインストール

Windowsでは、Windowsパッケージマネージャーを利用できます。コマンドプロンプトまたはPowerShellのウィンドウで**winget install openssl**を実行すると、OpenSSLの最新の安定版と必要な依存関係がすべて自動的にダウンロード・インストールされます。

```powershell
winget upgrade
winget install openssl
winget search openssl
```

macOSでは、macOSで広く使われているパッケージマネージャーのHomebrewを、ターミナルアプリケーションから利用できます。

```sh

brew install openssl
```

## 4DでOpenSSLを使う理由

4Dには多くの暗号処理のためのビルトインコマンドが用意されていますが、複雑な暗号処理においては、OpenSSLが依然として業界標準です。4D.SystemWorkerを活用すると、次のような利点があります：

- 非同期実行：コールバックパターンを使用した非同期処理により、アプリケーションの応答性を維持できます。ノンブロッキング実行のため、重い暗号化タスクをバックグラウンドで実行している間もUIはスムーズに動作します。
- 柔軟性：OpenSSLのすべてのパラメーターを利用できます。
- カスタマイズ性：OpenSSLのコマンドとパラメーターを組み合わせて、サードパーティ製ソフトウェアの要件に対応できます。
- ID情報の自動化：カスタムのOpenSSL設定ファイル（**openssl.cnf**）を利用して、一意のシリアル番号や識別名（DN：Distinguished Name）などの組織情報を、ユーザーが手動で入力することなく証明書に自動的に追加できます。

## 非同期アーキテクチャ

### SystemWorkerクラスのパターン

本OpenSSL統合の実装は、4DのSystemWorkerドキュメントで推奨されている、クラスベースのコールバックパターンに従っています。このアーキテクチャには、ほかの方法と比べて大きな利点があります。すべてのコールバック処理を1つのクラスに集約することで、コードベースが整理され、システムの理解や変更が容易になります。OpenSSLWorkerクラスの構造により、Thisキーワードを使った高度な状態管理が可能になり、複数回のコールバック呼び出しにわたってデータやコンテキストを保持できます。

OpenSSLWorkerクラスは、OpenSSLコマンドの実行中にSystemWorkerのすべてのコールバックを管理する中核です。4DのSystemWorkerドキュメントによると、すべてのコールバック関数は2つのオブジェクト引数を受け取ります。第1引数は常にSystemWorkerオブジェクト自体で、response、responseError、exitCodeなどのプロパティにアクセスできます。第2引数はイベントオブジェクトで、コールバックの種類に関するメタデータや、場合によってはデータの断片（チャンク）を含みます。このクラスには、コマンド実行のライフサイクルの各段階に対応する、5つのコールバック関数が実装されています。

onResponse関数は、レスポンス全体を受信したときに呼び出されますが、実際には、出力を逐次処理するためにonDataコールバックのほうがよく使われます。onData関数は、標準出力ストリームからデータのチャンクが届くたびに呼び出されるため、時間のかかる処理の進捗を監視するのに最適です。同様に、onDataErrorは標準エラーストリームから届くデータを処理します。onError関数は、実行ファイルが見つからない、権限がないといった、実行時の異常な状態を表すエラーを捕捉します。最後に、onTerminate関数は、成功・失敗にかかわらず実行の終了時に必ず呼び出されるため、後処理や最終的なステータスの判定に最適です。

```4d
Function onResponse($param1 : Object; $param2 : Object)
// $param1 - SystemWorker
// $param2.type - "response"
customLog($param2.type)
```

クラスのコンストラクターは、実行が成功したときに呼び出される完了関数を受け取ります。これにより、OpenSSLの処理ごとに、実行後の動作を個別に定義できます。

timeoutプロパティは特に重要です。このプロパティはSystemWorkerインスタンスによって自動的に読み取られるため、コールバック関数内で手動でタイムアウトを管理しなくても、プロセスが無期限にハングするのを防ぐことができます。

### Execute_OpenSSLAsynchメソッド

中核となる実行メソッドは、4DのSystemWorkerクラスを高度にラップしたもので、ワーカープロセス管理の複雑な処理を自動的に行います。このメソッドは、まず自身がワーカープロセス内で実行されているかどうかを検出します。そうでない場合はワーカーを作成します。これは、4Dのドキュメントに記載されている重要な要件です。

SystemWorkerクラスのドキュメントには、次のように明記されています：

> ***注：*** *[...] wait()を使用しない場合（非同期呼び出し）、コールバック関数が呼び出されるためには、プロセスはNew processではなく、CALL WORKERで作成されたワーカーでなければなりません。*

```4d
If (Process info(Current process).type#Worker process)
    CALL WORKER("OpenSSL_Worker"; Current method name; $command; $onComplete)
    return
End if
```

ワーカー内で実行されると、メソッドはアプリケーションのストレージ設定からOpenSSLのインストールパスを検証し、ディレクトリ名に含まれる空白に対応するためにパスを適切に引用符で囲んで、完全なコマンド文字列を組み立てます。次に、完了コールバックを渡してOpenSSLWorkerクラスをインスタンス化し、そのクラスオブジェクトをoptions引数としてSystemWorkerインスタンスを作成します。ここで重要なのは、このメソッドがSystemWorkerのwait()関数を呼び出さないことです。wait()を呼び出すと実行がブロックされ、非同期アーキテクチャの意味がなくなってしまいます。代わりにメソッドはすぐに戻るため、呼び出し元のコードは実行を継続でき、その間OpenSSLコマンドはバックグラウンドで実行され、コマンドのライフサイクル中にイベントが発生するたびにコールバックが呼び出されます。

このアーキテクチャにより、真のノンブロッキング実行が実現し、時間のかかる可能性がある暗号処理の間もユーザーインターフェースは応答性を保ちます。ワーカーの自動検出と自己生成の仕組みにより、非同期の動作は呼び出し元のコードからは意識されません。呼び出し元は、コマンドとコールバック関数を指定してExecute_OpenSSLAsynchを呼び出すだけでよく、背後にあるワーカープロセスの要件を理解する必要はありません。この抽象化により、OpenSSLの処理を実装する開発者の負担が大幅に軽減されると同時に、4DのSystemWorkerクラスのリファレンスに記載された要件も確実に満たされます。

### onFileGeneratedコールバック

onFileGeneratedコールバックプロジェクトメソッドは、暗号処理のワークフローにおけるすべてのファイル生成処理に共通して再利用できる汎用ハンドラーです。秘密鍵、CSR、証明書、署名付きXMLファイルごとに個別の完了ハンドラーを実装するのではなく、この統合されたコールバックが、どのファイルが生成されたか、正常に完了したときにそのファイルをどう扱うかを示す引数を受け取ります。この設計により、コードの重複が大幅に減り、アプリケーション内のすべてのOpenSSL処理で、完了後の動作が一貫したものになります。

```4d
Execute_OpenSSLAsynch($cmd; Formula(onFileGenerated($keyPath)))
```

このコールバックは、ファイルパスを4DのFileオブジェクトに変換します。Fileオブジェクトを使うと、platformPathプロパティを含む、オブジェクト指向のファイル操作を利用できます。platformPathプロパティは、SHOW ON DISKコマンドに欠かせません。SHOW ON DISKは、生成されたファイルをオペレーティングシステムのファイルブラウザー（macOSではFinder、Windowsではエクスプローラー）で表示するコマンドで、プラットフォーム固有の形式のパスを必要とします。Windowsでは、スラッシュを使ったPOSIX形式のパスをSHOW ON DISKが解釈できないため、クロスプラットフォームの互換性を保つにはplatformPathへの変換が不可欠です。処理の完了時に生成されたファイルをユーザーに表示することで、処理が成功したことをすぐに目で確認できると同時に、生成された暗号関連リソースを確認したり、さらに処理したりするために簡単にアクセスできます。

## OpenSSL設定の自動化

暗号処理のワークフローの基盤となるのは、**openssl.cnf**設定ファイルです。このファイルは、証明書生成の自動化と、処理全体の一貫性の確保において中心的な役割を果たします。CSR（証明書署名要求）の作成時に手動入力に頼ると、ミスが起こりやすく、時間もかかります。そこで、設定ファイルに基づくアプローチを採用し、一貫性を確保するとともに、規制の枠組みで義務付けられている特定のシリアル番号を含めるといった、厳格なID情報の要件を満たします。この自動化は、組織情報は異なっても形式や構造は一貫した証明書を、頻繁に生成する必要がある本番環境で特に役立ちます。

### 設定ファイルの構造

証明書のサブジェクトを識別する識別名（DN）のフィールドを自動化するために、特定の構造を持つ設定ファイルを使用します。この設定で最も重要なディレクティブは**prompt = no**で、4D System Workerによるヘッドレス実行に欠かせません。このディレクティブがないと、OpenSSLは実行を一時停止して、ターミナルからの対話的な入力を待ちます。これは、バックグラウンドプロセスで実行されるSystemWorkerでは成り立ちません。**prompt = no**を設定すると、OpenSSLはユーザーとのやり取りなしに設定ファイルで指定された値を使用するため、証明書生成を完全に自動化できます。

```text
[ req ]
default_bits       = 2048
default_md         = sha256
distinguished_name = req_distinguished_name
prompt             = no

[ req_distinguished_name ]
C              = US
ST             = California
L              = San Francisco
O              = My Company Inc.
OU             = IT Department
CN             = www.mycompany.com
serialNumber   = SRL-12-345678966
```

識別名の`serialNumber`フィールドには特に注意が必要です。政府の規制を受ける電子インボイスシステムや、企業の本人確認の仕組みでは、このフィールドが必須となることがよくあります。このフィールドの形式は管轄によって異なり、たとえば欧州連合（EU）諸国ではVAT番号、その他の地域では納税者番号、企業環境では社内のデバイス識別子などが求められる場合があります。

## 暗号関連リソースの生成

本テクニカルノートでは、ソフトウェアアプリケーションのさまざまな場面で利用される、各種の暗号関連リソースの生成に焦点を当てます。取引先との暗号化されたデータ交換、SSL/TLSによるWebサーバー通信の保護、ドキュメント認証のためのデジタル署名の実装など、どのような用途であっても、暗号関連リソースは現代の安全なアプリケーションの基盤です。生成のワークフローは、最も基本的な要素である秘密鍵から始まり、論理的な順序で進みます。より高度な派生的な暗号関連リソースは、この基盤の上に構築されます。

### 秘密鍵の生成

ワークフローは、以降のすべての暗号処理の「信頼の起点（root of trust）」となる秘密鍵から始まります。秘密鍵は、インフラストラクチャ全体の中で最も機密性の高い要素です。この鍵を持つ者は、その鍵から派生した証明書に関連付けられたIDになりすましたり、対応する公開鍵で暗号化されたメッセージを復号したりできるからです。本統合では、2048ビットのモジュラスを持つRSAアルゴリズムを使用します。これは現在、一般的な4Dアプリケーションにとって、高いセキュリティと計算性能のバランスが最も優れた選択肢です。4096ビットの鍵はさらに大きなセキュリティマージンを提供しますが、生成と使用の両方で処理能力を大幅に多く必要とするため、ほとんどのアプリケーションでは2048ビットの鍵が推奨されます。

RSA秘密鍵を生成するOpenSSLコマンドは単純です：

```sh
genrsa -out "private_key.key" 2048
```

**genrsa**サブコマンドはRSA秘密鍵の生成をOpenSSLに指示し、**-out**パラメーターは鍵を書き出す出力ファイルのパスを指定します。最後の引数2048は鍵のサイズをビット単位で示します。このコマンドを実行すると、OpenSSLはRSA鍵ペアの作成に必要な数学的演算を行い、秘密鍵の部分を指定されたファイルに書き出します。非同期実行パターンでは、4Dのメソッドは鍵の生成を開始した直後に戻り、OpenSSLが鍵ファイルの作成と書き出しを終えた時点で完了コールバックが呼び出されます。デモの都合上、鍵の生成にはメソッドの同期バージョンを使用していますが、デモアプリケーションには、すべてのメソッドの非同期バージョンも用意されています。

### 証明書署名要求の生成

証明書署名要求は、暗号関連リソースを生成するワークフローの次のステップです。CSRは、署名付き証明書の発行を認証局（CA：Certificate Authority）に申請するための正式な要求です。開発・テスト環境では、自己署名に使用することもできます。CSRには、先に生成した秘密鍵から取り出した公開鍵と、最終的な証明書に埋め込まれるID情報が含まれます。このID情報はX.509標準の構造に従い、国（C）、都道府県（ST）、市区町村（L）、組織（O）、部門（OU）、コモンネーム（CN）などのフィールドで構成されます。

**-config**フラグで自動化用のopenssl.cnfファイルを参照することで、ターミナルからの対話的な入力や4Dメソッドへの値のハードコーディングなしに、シリアル番号とすべての識別名フィールドを自動的に挿入できます。この設定ファイルに基づくアプローチには、ID情報をアプリケーションロジックから分離できる、組織情報が変わったときにシステムを保守しやすい、異なる設定ファイルをプログラムで作成してCSRを動的に生成できる、といった大きな利点があります。

CSRを生成するOpenSSLコマンドの全体は次のとおりです：

```sh
req -new -key "private_key.key" -out "request.csr" -config "openssl.cnf"
```

### コマンドパラメーターの説明

| パラメーター | 説明 |
|:---|:---|
| **-new** | 新しい証明書要求を生成します |
| **-key** | 使用する秘密鍵ファイルを指定します |
| **-out** | CSRの出力ファイル名 |
| **-config** | OpenSSL設定ファイルのパス |

### 自己署名証明書の生成

信頼された認証局を必要としない社内テスト、開発環境、プライベートなデータ交換などの場面では、自己署名証明書が実用的な解決策となります。この種類の証明書は、秘密鍵をCSRまたは設定ファイルで定義されたID情報と結び付け、暗号化やデジタル署名に使用できる有効なX.509証明書を作成します。「自己署名」とは、別の認証局の鍵ではなく、その証明書が証明する秘密鍵そのもので署名されていることを意味します。自己署名証明書は、ブラウザーの信頼性の警告が表示されるため、一般公開するWebサイトには適していませんが、社内アプリケーションやテスト環境ではまったく問題なく使用できます。

自己署名証明書を生成するOpenSSLコマンドは、CSRの生成と証明書への署名を1回の操作で行います：

```sh
req -new -x509 -key "private_key.key" -config "openssl.cnf" -out "certificate.crt" -days 365
```

ここで決め手となるのが**-x509**フラグで、証明書署名要求の代わりに自己署名証明書を出力するようOpenSSLに指示します。**-days**パラメーターは証明書の有効期間を日数で指定します。この期間を過ぎると証明書は期限切れとみなされ、アプリケーションはその証明書を信頼しなくなります。

### XMLファイルへの署名

暗号処理パイプラインの最後のステップは、XMLドキュメントへのデジタル署名の適用です。これは、金融関連のワークフローで頻繁に求められる要件です。多くの電子インボイスシステム、発注システム、サプライチェーン管理プラットフォームでは、真正性と完全性を保証するために、XMLドキュメントにデジタル署名を付けることが求められます。これは、XMLデータをPKCS#7署名コンテナーで包むS/MIME（Secure/Multipurpose Internet Mail Extensions）標準を使用して実現します。この署名形式により、受信者は送信者の身元（証明書の検証による）とデータの完全性（署名後に内容が変更されていないことの検証による）の両方を確認できます。

4Dアプリケーションは、OpenSSLのsmimeコマンドを使用してバイナリ署名の操作を行い、パスワードで保護された秘密鍵を使って、PEM形式の.p7sファイルを出力します。署名が有効で、受信側のシステムに受け入れられるものにするためには、コマンドを組み立てる際に、いくつかの重要なパラメーターを正しく指定する必要があります。

```4d
$cmd:="smime -sign -binary -nodetach"
$cmd+=" -in "+Char(34)+$pathXMLIN+Char(34)
$cmd+=" -out "+Char(34)+$pathXMLOUT+Char(34)
$cmd+=" -signer "+Char(34)+$pathCert+Char(34)
$cmd+=" -inkey "+Char(34)+$pathKey+Char(34)
$cmd+=" -passin pass:"+$password
$cmd+=" -outform PEM"
```

このコマンドのいくつかのフラグは、署名の有効性にとって非常に重要なため、詳しく説明します。**-binary**フラグは、入力ファイルをテキストではなくバイナリデータとして扱うようOpenSSLに指示し、署名を無効にしてしまう改行コードの変換を防ぎます。XMLファイルはテキストベースですが、改行コードや空白を含むバイト列をそのまま保持するために、常にバイナリモードで署名する必要があります。これらのわずかな変更でも、署名の検証は失敗するからです。**-nodetach**フラグは、元のXMLの内容を署名とともに出力ファイルに含めるよう指定し、自己完結した署名付きメッセージを作成します。受信者が元の内容と署名の両方を1つのファイルで受け取れるため、ほとんどのドキュメント交換ではこれが標準的な方法です。**-passin pass:**オプションは暗号化された秘密鍵のパスワードを指定するもので、実際のパスワードをコロンの直後に続けて記述します。最後に、**-outform PEM**は、出力をPEM（Privacy-Enhanced Mail）形式にします。PEMはBase64でエンコードされた表現で、メールシステムやドキュメント管理プラットフォームとの互換性が高い形式です。

### 4D Webサーバーとの連携

このOpenSSL統合で生成したSSL/TLS証明書で4D Webサーバーを保護するには、証明書と秘密鍵のファイルを、4Dが参照する特定の場所にコピーする必要があります。SSL/TLSを有効にして4DのWebサーバーを起動すると、4Dはプロジェクトフォルダーのルートディレクトリにあるcert.pemとkey.pemという名前のファイルを自動的に探します。生成した.pemファイルと.keyファイルを、この標準の名前と場所にリネームしてコピーすることで、OpenSSLで生成した証明書を4DのビルトインWebサーバーにスムーズに組み込むことができます。

実装では、4DのFileオブジェクトとFolderオブジェクトを使用して、Resourcesフォルダー内のコピー元ファイルとプロジェクトフォルダー内のコピー先を特定し、fk overwriteオプションを指定した.copyTo()メソッドで、既存の証明書を新しく生成したものに置き換えます。このコピー処理はユーザーインターフェースのボタンから実行できるため、管理者はアプリケーションを再起動したり、ファイルシステム上のファイルを手作業で操作したりすることなく、証明書を更新できます。

証明書ファイルを配置したら、HTTPとHTTPSの両方の設定を制御できる4D.WebServerクラスを使用して、プログラムからWebサーバーを設定・起動します。実装では、まず実行中のサーバーインスタンスを停止して、新しい証明書の設定でクリーンに再起動できるようにします。次に、ポート80のHTTPとポート443のHTTPSの両方を明示的に有効にする設定オブジェクトを作成し、その設定を渡してstart()メソッドを呼び出します。

## ベストプラクティスとセキュリティ上の考慮事項

### 証明書の管理

適切な証明書管理は、生成と保存の技術的な実装だけにとどまりません。暗号関連リソースのライフサイクル全体を通じてセキュリティを確保する、包括的なライフサイクル管理の実践が求められます。

秘密鍵は安全な場所に保存し、適切なファイル権限を設定して、アクセスを必要とする最小限のユーザーとプロセスに限定する必要があります。macOSやLinuxなどのUnix系システムでは、通常、鍵の生成直後に**chmod**コマンドを使用して、ファイル権限を600（所有者のみ読み書き可能）に設定します。Windowsシステムでは、NTFSのアクセス許可を使用して、同様にファイルの所有者だけにアクセスを制限します。

いくら強調してもしすぎることのない絶対的な要件として、秘密鍵をGitなどのバージョン管理システムに決してコミットしてはいけません。プライベートリポジトリであっても、バージョン管理システムはファイルのすべての履歴を保存するように設計されているため、秘密鍵をバージョン管理に保存することは許容できないセキュリティリスクとなります。誤って一度でもコミットした鍵は、現在のバージョンから削除した後もリポジトリの履歴に残り続けます。実際、秘密鍵やAPIの認証情報が、GitHubなどのプラットフォーム上の公開リポジトリに誤ってコミットされたことが原因で、多くの重大なセキュリティ侵害が発生しています。開発者は、.gitignoreファイルやそれに相当する仕組みを使って、.keyや.pemなどの拡張子を持つファイルが自動的にバージョン管理から除外されるようにする必要があります。

### 本番環境への展開

暗号システムを本番環境に展開する際は、開発やテストとは大きく異なる場合がある、業界標準とベストプラクティスに従う必要があります。インターネット経由でアクセスされる一般公開のサービスでは、ブラウザーのセキュリティ警告によってユーザー体験が損なわれるため、自己署名証明書は使用できません。本番システムでは、ブラウザーやオペレーティングシステムのトラストストアに含まれている、信頼された認証局（CA）が発行した証明書を使用する必要があります。Let's Encryptは多くの用途に適した無料の自動化された証明書を提供しており、商用のCAは、EV（Extended Validation）証明書や追加のサポートサービスを提供しています。

## よくある問題のトラブルシューティング

### OpenSSLが見つからない

最も基本的な問題は、OpenSSLの実行ファイルが見つからないことです。この場合、指定されたコマンドが見つからないことを示すエラーメッセージが表示されます。この問題は通常、OpenSSLがインストールされていない、新しくセットアップしたシステムや、アプリケーションの設定で指定したパスとは異なる標準以外の場所にOpenSSLがインストールされているシステムで発生します。トラブルシューティングでは、まずターミナルまたはコマンドプロンプトを開いて**openssl version**を実行し、OpenSSLがインストールされていることを確認します。OpenSSLが正しくインストールされ、システムのPATHからアクセスできる場合は、バージョン情報が表示されます。4Dアプリケーションでは、ユーザーがOpenSSLのカスタムフォルダーを選択して、OpenSSLの実行ファイルを指定できます。アプリケーションは以降、そのファイルを使用します。つまり、デモアプリケーションを通常どおり使用する場合、OpenSSLをシステムの環境変数に追加する必要はありません。

### XML署名が無効になる

まず、OpenSSLの**smime**コマンドに**-binary**フラグが含まれていることを確認します。このフラグがないと、OpenSSLはプラットフォームに応じて**\n**を**\r\n**に、またはその逆に変換するなど、XMLデータの改行コードを変換することがあります。デジタル署名はデータの正確なバイト列に対して計算されるため、XMLが機能的に同等で整形式のままであっても、改行コードが変更されると署名は無効になります。**-binary**フラグを指定すると、OpenSSLはバイト列を一切変換せずにそのまま保持します。

## まとめ

4Dの非同期SystemWorkerクラスとOpenSSLを統合することで、4Dアプリケーションに暗号処理を実装するための堅牢なソリューションが得られます。コールバックベースのアーキテクチャにより、時間のかかる可能性がある暗号処理の間もアプリケーションは応答性を保ち、使い続けることができます。同時に、より高レベルの技術にありがちな制限を受けることなく、OpenSSLのコマンドラインインターフェースの機能と柔軟性を最大限に活用できます。本書で紹介したパターンとプラクティスに従えば、秘密鍵、証明書署名要求、自己署名証明書、署名付きXMLドキュメントの生成といった複雑な暗号処理のワークフローを、自信を持って実装できます。

この実装の主な成果は、ノンブロッキングなユーザーインターフェース動作を伴う真の非同期実行、処理の複数の段階でエラーを捕捉・報告する包括的なコールバックシステムによる堅牢なエラー処理、そしてWindowsとmacOSの両方でシームレスに動作する自動パス処理とプラットフォーム検出によるクロスプラットフォームの互換性です。セキュリティコンプライアンスとトラブルシューティングのための監査証跡を残すログ機能も、重要な要素です。ワーカーの自動検出と自己生成の仕組みによってSystemWorkerのコールバックの要件の複雑さが隠されるため、背後にある技術的な詳細をよく知らない開発者でも、非同期処理を利用できます。
